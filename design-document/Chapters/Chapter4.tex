\section{Behavioural and Interaction Design}
\subsection{Use-Case Model}
\diagram[dy]{use-case}{Use Cases}

The Litho publishing ecosystem encompasses seventeen formal use cases organized across five core functional subsystems, supporting five distinct external actors:
\begin{enumerate}
    \item \textbf{Author / Student:} Technical writers and researchers creating documents, compiling PDFs, inspecting marketplace templates, and extracting source from compiled artifacts.
    \item \textbf{Template Publisher:} Institutional formatting leads and designers authoring, validating, and submitting reproducible template packages.
    \item \textbf{Marketplace Maintainer:} Curators who review automated security baselines, attest capabilities, and publish approved listings.
    \item \textbf{AI Assistant:} Autonomous agents interacting with Litho tools over the Model Context Protocol (MCP).
    \item \textbf{CMS Site / External Client:} Third-party content platforms and integration pipelines invoking automated conversion over REST APIs and webhooks.
\end{enumerate}

Each use-case specification below is structured according to its key architectural components: Actor, System, Goal (Objective), Preconditions, Trigger, Basic Flow (Main Scenario), and Alternate / Exception Flows, as presented in Tables~\ref{tab:uc01} through~\ref{tab:uc17}.

Each of the five delivery channels is a thin adapter over the same conversion core. The CLI, VS Code extension, conversion web app, MCP server, and hosted conversion API therefore depend on the pipeline through one conversion interface (INT-01) instead of reimplementing parsing or code generation. Inside the pipeline, the Tokenizer and Parser, Template Binder, LaTeX Codegen, and Metadata I/O components realize the parse--bind--generate--embed sequence, while the Template Loader and Package Validator isolate manifest, schema, and asset handling. The pipeline requires the sandboxed Tectonic engine for compilation (INT-02) and exposes metadata embedding and extraction so that the original Markdown source can be recovered from a generated PDF.

The marketplace is deliberately kept outside the conversion path: it depends on GitHub for the curated issue registry (INT-04) and on the counters database for hearts and downloads (INT-10), so a registry or counter outage does not block local builds. AI authoring and review consumes the LLM provider and also invokes the shared pipeline, which keeps generated templates subject to the same validation and compilation rules as hand-written ones. The documentation website remains a static Next.js site built from the documentation repository and therefore has no runtime dependency on the conversion core.

\section{Data Design and Management}
\label{sec:data-design}

\subsection{Registry and Persistence Design}
Litho does not use an application database for the template registry. The published registry is derived from GitHub issues that maintainers review and label as listed, while each template's linked repository and releases hold its manifest, assets, and version history. A small application database stores only the per-template heart and download counters, keyed by template identifier. Figure~\ref{fig:data-model} models the resulting registry and counter records.

The schema separates a rebuildable read model from the only mutable application data. The \texttt{templates} table is keyed by \texttt{template\_id}, the stable slug shared by the CLI, MCP server, and API; \texttt{issue\_number} and \texttt{repo\_full\_name} are unique, so one reviewed issue or repository cannot produce two listings. \texttt{template\_tags} is a junction table with a composite primary key over \texttt{(template\_id, tag)} and a secondary index on \texttt{tag} for tag-filtered browsing. Each template has at most one \texttt{template\_counters} row, which shares the template key, defaults both counters to zero, and enforces non-negative values; indexes on \texttt{hearts} and \texttt{downloads} keep the ``most hearted'' and ``most downloaded'' orderings cheap.

Registry rows are written by the periodic GitHub sync, which upserts listings and tags from reviewed issues and the latest release manifest, so losing the database costs a re-sync rather than the registry itself. Delisted templates keep their rows and counters for 90 days so that reinstatement preserves engagement history, after which the sync job purges them. No user accounts or visitor identifiers are stored: heart and download increments are aggregated per template, so the counters table contains no personal data.
